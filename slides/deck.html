RAG 是什麼？
讓 LLM 先查資料再回答

Retrieval-Augmented Generation，檢索增強生成——
把「閉書考試」變成「開書考試」。

01 · 問題

LLM 只靠「記憶」回答，會出什麼事？

知識難更新

知識存在權重裡，世界變了就得重新訓練。

無法追溯

看不出答案是根據什麼來的，很難檢查。

會幻覺

不知道時也可能講得很有自信。

02 · 核心想法

開書考試：參數記憶＋可查的資料庫

  • 參數記憶：生成模型本身（原始論文用 BART）
  • 非參數記憶：可檢索的文件索引（Wikipedia 切成 21M 個段落）
  • 中間用檢索器（DPR）去查

換索引＝換知識

問 82 位換過職位的世界領袖：索引年份對得上時答對 70% / 68%，對不上時只剩 12% / 4%。

→ 不用重新訓練，換資料就能更新。

03 · 流程

RAG 的三個步驟（Retrieve-Read）

① 建索引離線做一次：清理文件 → 切段（chunk）→ 嵌入（embedding）→ 存進向量資料庫
→
② 檢索把問題也轉成向量，找出最相似的 top K 段
→
③ 生成問題＋段落組成 prompt，交給 LLM 回答

這個最基本的版本叫 Naive RAG。接下來會看到它的坑，以及怎麼補。

04 · 怎麼「找」

嵌入找意思，BM25 找字面

向量嵌入

擅長「意思相近」。但查「Error code TS-999」時，可能只找到一般錯誤碼說明。

BM25

字面比對，能精確找到寫著 TS-999 的那一段。

實務上兩個一起用（混合檢索），再用 rank fusion 合併、去重。

05 · 坑一

檢索越多段，答得越好嗎？

  • U 型曲線：答案在中間最容易被忽略
  • GPT-3.5-Turbo 不看文件 56.1%，答案藏中間時可能更差
  • 從 20 段加到 50 段只多約 1.5%
06 · 坑二

Naive RAG 的三類問題

檢索不準

抓錯段落，或漏掉真正相關的段落。

生成仍幻覺

有查到資料，答案還是可能沒照著寫。

整合困難

多段內容重複，抓不到哪段最重要。

而且切塊會丟掉上下文：一段只寫「營收成長 3%」，卻沒寫是哪家公司、哪一季。

07 · 解法一

Advanced RAG：把「查」這件事做好

  • 檢索前：改寫查詢、HyDE
  • 檢索後：rerank、壓縮上下文
  • Contextual Retrieval：每段先加 50-100 tokens 說明再建索引

08 · 解法二

Self-RAG：需要時才查，查完自己檢查

Retrieve 要不要查？
IsREL 資料相關嗎？
IsSUP 答案有被支持嗎？
IsUSE 答案有用嗎？

效果

PopQA：Self-RAG 13B 55.8，ChatGPT 29.3。

但不是每項都贏：ARC-Challenge 上 ChatGPT 的 75.3 仍較高。

09 · 評估

怎麼知道 RAG 做得好？分開檢查

Context relevance

查到的內容精準嗎？

Faithfulness

被支持的陳述數 ÷ 全部陳述數

Answer relevance

答案有回應問題嗎？

RAGAS 不需要標準答案；和人類判斷一致率 0.95 / 0.78 / 0.70，context relevance 最難評。

10 · 何時使用

一定要用 RAG 嗎？

長 prompt

知識庫小於 200,000 tokens（約 500 頁）：整份放進 prompt 就好。

RAG

要常更新知識、要能追溯來源。

微調

要改變風格、行為、術語。

RAG 和微調不互斥，結合使用可能效果最好。

11 · 小測驗

點一下看答案

Q1 檢索到 50 段一定比 20 段好？

不一定。表現早就飽和，答案在中間還容易被忽略。

Q2 要查精確的錯誤代碼，該加哪種檢索？

BM25（字面比對），和嵌入一起做混合檢索。

Q3 想知道答案有沒有亂講，看哪個指標？

Faithfulness：答案的陳述有沒有被檢索內容支持。
